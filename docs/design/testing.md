# Testing and performance verification

> Status: Draft · Set up in [M0.1](../milestones/m0.md#work-packages), budgets verified in M0.5

OverBench runs on macOS, Windows and Linux, and most of what can differ between them lives in the agent host. The strategy follows from that: test the protocol and process logic automatically on all three platforms with a fake agent, and check the interface and the real agents by hand before each milestone is signed off.

## Layers

| Layer       | Tool                            | What it covers                                                                                                                                                                                                                                                                                                                    | Where it runs          |
| ----------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| Unit        | Vitest                          | `applyPatches` and `applyPatchInPlace`, the ACP v1 mapper, request validators, shell environment parsing, command lookup with `PATHEXT`, shell quoting, path canonicalization, persistence migrations and atomic writes, matching the system's language, and the [message catalogs](./localization.md#catalogs) of both languages | CI on all platforms    |
| Integration | Vitest with the fake agent      | The host's session logic against a real ACP peer: turns, permissions, cancellation, load and resume, auth errors, unknown updates                                                                                                                                                                                                 | CI on all platforms    |
| Process     | Vitest, spawning the fake agent | Stdio framing, the termination sequence and process tree cleanup, crash detection                                                                                                                                                                                                                                                 | CI on all platforms    |
| Interface   | The running app                 | Every screen and state in both themes and both languages, with reduce-motion on, against the fake agent; IME input in the composer; the thread's scroll-following thresholds                                                                                                                                                      | By hand, each platform |
| Real agents | The running app                 | The M0 acceptance tasks with Claude Code, Codex and OpenCode                                                                                                                                                                                                                                                                      | By hand, each platform |
| Performance | CDP script and the fake agent   | The [M0 budgets](../milestones/m0.md#performance-budgets) on a production build                                                                                                                                                                                                                                                   | By hand, each platform |

React components have no automated tests in M0; they are checked by running the app, as [AGENTS.md](../../AGENTS.md#definition-of-done) requires for every UI change.

## Unit and integration tests

- Test files sit next to the code they test, named `*.test.ts`.
- `vitest.config.ts` at the root runs in the `node` environment and resolves the `@shared` and `@renderer` aliases like `electron.vite.config.ts`.
- `pnpm test` runs everything once; `pnpm test:watch` runs Vitest in watch mode.
- The mapper is tested with fixtures: recorded or hand-written sequences of ACP messages, each with the patches and final snapshot it must produce. A bug found with a real agent becomes a fixture first.
- Integration tests connect the host's session layer to the fake agent in-process: the agent's `AgentApp` and the host's client talk through an in-memory stream pair (`inProcessTransport` in `src/agent-host/acp/connection.ts`), so they need no subprocess and stay fast. The host's connection code therefore accepts either a process's stdio or an in-process agent.
- `src/agent-host/testing/harness.ts` holds what they share. `startTestHost()` runs a whole host, as `index.ts` builds it, on a temporary data directory, with an in-process launcher for the fake agent, a stubbed shell environment and no other agent found. `TestPort` stands in for a renderer port: it structured-clones every message both ways, as a real `MessagePort` does, so a payload that would not survive the port fails the test, and it keeps a replica of each watched thread by applying the batches with `applyPatches`, failing on any `seq` gap. Tests compare that replica with `sessions.snapshot`.
- Timings that matter to a test are options rather than constants: the 16 ms flush, the 10 s cancel fallback, the `initialize` timeouts and the idle stop, so tests run them in milliseconds instead of with fake timers.
- Process tests spawn `tools/fake-agent/main.ts` with `process.execPath`, never a shell, so they run the same on every platform. They cover framing and a clean EOF stop, a forced stop of a process tree, `SIGKILL` escalation (skipped on Windows, which has no `SIGTERM` to ignore; `taskkill /F` always ends the tree), a whole host whose agent crashes mid-turn, closing the session, and starts again for the next prompt, what an agent leaves in groups of its own after a stop and a crash, and the leftovers a host stops at start, without touching a process that took one of their pids.
- The [adapter install](./agent-host.md#installing-adapters) is tested with the real npm, offline: a fixture package packed with `npm pack` is installed from its tarball, which the installer accepts as the dependency spec in place of a registry version. The tests cover the atomic rename, a failed and a timed-out install, leftover `.partial-*` directories, resolving `bin`, the fallback to an older version and the cleanup after an update. CI runs them on all three platforms, which covers `npm.cmd` on Windows.
- Tests that touch the file system use a fresh temporary directory.

## Fake agent

`tools/fake-agent/` is an ACP agent built with the SDK's `agent()` API. It never calls a model; it plays scripted scenarios.

- **Running it**: `tools/fake-agent/main.ts` runs directly on Node.js through type stripping, either with Electron's own Node.js (`ELECTRON_RUN_AS_NODE=1`) or with any Node.js 22.18 or later. It has no build step, so its code uses only erasable TypeScript syntax and relative imports with `.ts` extensions; its folder has a `package.json` with `"type": "module"`. `tsconfig.tools.json` type-checks it with `erasableSyntaxOnly` and `allowImportingTsExtensions`, and `pnpm typecheck` includes it.
- **In process**: `tools/fake-agent/agent.ts` exports `createFakeAgent(options)`, which returns the SDK's `AgentApp`. Integration tests connect it to the host's session layer through an in-memory stream pair; `options.exit` replaces `process.exit` so the `crash` scenario closes the connection instead of ending the test run. Tests load it with a dynamic `import()` of its file URL, because the host's `tsconfig.node.json` does not allow `.ts` import extensions; `tsconfig.tools.json` still type-checks it.
- **Choosing a scenario**: the prompt text selects it with `/scenario <name> [flags]` or `/<name> [flags]`, so one agent process can run any scenario; any other text runs the default (`FAKE_AGENT_SCENARIO`, else `basic-turn`). The agent advertises every scenario as a slash command, plus `scenario` and `compact`.
- **Protocol surface**: it uses the SDK's `unstable` v1 entrypoint so it can send the subagents RFD updates, and it advertises `loadSession`, `session/list`, `session/resume`, `session/close`, `session/delete`, logout, one `agent` sign-in method (`fake-login`) and, when the client supports terminal sign-in, one `terminal` method (`fake-terminal-login`, which runs `main.ts --login`). Its config options are a mode select (Ask, Code, Plan), a grouped model select with three models, a `thought_level` select and one boolean (Fast mode). It pushes `_auth/status_update` once after `initialize` and whenever its sign-in state changes, and sends `usage_update` with `_meta["_claude/rateLimit"]` for the five-hour and weekly windows at the end of most turns, with `utilization` as a fraction and `resetsAt` in Unix seconds, as Claude Code does. Each prompt response's `usage` holds the turn's own counts, as the real adapters send them. It sends subagent updates only when the client advertised `clientCapabilities.subagents`; the RFD has no agent capability.
- **In the app**: development builds list it in the agent catalog as Fake agent. A production build lists it only when started with `OVERBENCH_FAKE_AGENT` set to the path of `main.ts`, which is how the performance runs use it. It is never packaged.

| Scenario               | What it does                                                                                                                                                                                                                                                    |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `basic-turn`           | A short answer with markdown (heading, list, code block, table, inline code, link) and one edit with a diff                                                                                                                                                     |
| `long-stream`          | 200 KB of markdown in 100-character chunks at a configurable rate (default 200 updates per second); `--rate`, `--size`                                                                                                                                          |
| `tool-storm`           | 500 tool calls, mixing reads, searches, edits, commands, fetches and thoughts, with two updates each; `--count`                                                                                                                                                 |
| `permission`           | A command that needs approval, offering all four option kinds; `--withdraw [ms]` withdraws the request after a delay                                                                                                                                            |
| `parallel-permissions` | Three tool calls asking for permission at the same time                                                                                                                                                                                                         |
| `cancel`               | A long turn that honors `session/cancel`; with `--ignore-cancel` it never confirms                                                                                                                                                                              |
| `crash`                | Exits mid-turn with a non-zero code (`--code`, default 3)                                                                                                                                                                                                       |
| `auth-required`        | Signs the agent out and fails the prompt with `auth_required`; `session/new`, `load`, `resume` and `prompt` then fail until `authenticate` or `main.ts --login`. The same prompt sent again in that session after sign-in answers, as the client's retry should |
| `large-history`        | Marks the session so that `session/load` replays 1,000 entries (`--entries` sets another size), which OverBench does only for a session it stored no thread of; the importable session `large-history-1` does the same, and importing `history-<n>` gives n     |
| `slow-start`           | Takes 20 s to answer `initialize`, printing progress to stderr; chosen at launch with `FAKE_AGENT_SCENARIO=slow-start`, since it happens before any prompt                                                                                                      |
| `all-updates`          | Sends every `session/update` variant once, including every content block kind, the subagent updates and an unknown `future_update`                                                                                                                              |
| `subagent`             | Announces a child session, sends it a `session_message`, streams its work including one permission request on the child, and ends the child with `idle`                                                                                                         |
| `plan`                 | A four-item plan whose items progress while the agent reads files                                                                                                                                                                                               |
| `thinking`             | A long thought streamed token by token, then an answer                                                                                                                                                                                                          |
| `background`           | A command with `run_in_background`, whose call ends at once, as Claude Code reports one to a client without terminals                                                                                                                                           |
| `usage`                | The `/usage` report as claude-agent-acp formats it, with the windows `usage_update` pushes and a model-scoped weekly window; `--plain` sends Claude Code's own plain text instead, as the adapter forwards it when its report fails or takes over 5 s           |
| `status`               | The `/status` report as codex-acp formats it, with the windows of `usage` and a credits line                                                                                                                                                                    |
| `context`              | The `/context` report as Claude Code writes it, twice under two message ids as Claude Code sends it, for the session's tokens                                                                                                                                   |

Without a scenario it plays `basic-turn`. `/compact` streams a compaction with its summary. Replies stream with tens of milliseconds between chunks, like a real agent.

Environment variables, read when the agent starts:

| Variable                             | Effect                                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `FAKE_AGENT_SCENARIO`                | The scenario for prompts that name none; `slow-start` also delays `initialize`                         |
| `FAKE_AGENT_RATE`, `_SIZE`, `_COUNT` | Defaults for `--rate`, `--size` (such as `200k`) and `--count`                                         |
| `FAKE_AGENT_DELAY_SCALE`             | Multiplies every delay; `0` runs scenarios as fast as possible, which the tests use                    |
| `FAKE_AGENT_SLOW_START_MS`           | Delays `initialize` by this long, printing progress                                                    |
| `FAKE_AGENT_AUTH=required`           | Starts signed out                                                                                      |
| `FAKE_AGENT_LEGACY_MODES=1`          | Reports modes through the legacy `modes` field instead of a mode config option                         |
| `FAKE_AGENT_HISTORY_ENTRIES`         | The size of the synthesized `large-history` replay (default 1,000)                                     |
| `FAKE_AGENT_LIST_PAGE`               | The `session/list` page size (default 50), to exercise `nextCursor`                                    |
| `FAKE_AGENT_RESUME_UNKNOWN=fail`     | `session/resume` of a session it does not know fails, as Claude Code's does                            |
| `FAKE_AGENT_NEW_SESSION_MS`          | Delays every `session/new` answer by this long, unscaled, for a slow hidden session                    |
| `FAKE_AGENT_WITHOUT`                 | Session capabilities to leave out, comma-separated, such as `close`                                    |
| `FAKE_AGENT_IGNORE_EOF=1`            | Keeps running after stdin closes, for the forced-stop process test                                     |
| `FAKE_AGENT_IGNORE_SIGTERM=1`        | Ignores `SIGTERM`, so a stop has to escalate to `SIGKILL`                                              |
| `FAKE_AGENT_SPAWN_CHILD=1`           | Starts a long-running child process and prints its pid to stderr, for process-tree cleanup             |
| `FAKE_AGENT_SPAWN_CHILD=detached`    | The same child in a process group of its own, as Claude Code runs a command                            |
| `FAKE_AGENT_SPAWN_CHILD=nested`      | A child in the agent's group that starts a grandchild in a group of its own, as Claude Code's CLI does |
| `FAKE_AGENT_LOGIN_MARKER`            | Where `main.ts --login` writes its sign-in marker (default: the temp directory)                        |

The fake agent keeps its sessions in memory. `session/load` replays what happened in the same process; a session it does not know, such as one from before a restart, gets a short synthesized history, and `session/resume` takes it up as a new one unless `FAKE_AGENT_RESUME_UNKNOWN=fail`.

## Continuous integration

`.github/workflows/ci.yml` runs on every push to `main` and every pull request. Its `check` job runs on `macos-latest`, `windows-latest` and `ubuntu-24.04`, the Ubuntu that [release builds](./updates.md#releases) use:

1. Install with `pnpm install --frozen-lockfile`.
2. `pnpm format:check`, `pnpm lint`, `pnpm typecheck`.
3. `pnpm test`, which includes the process tests that spawn the fake agent on each platform.
4. `pnpm build`, then `electron-builder --dir` to prove the app packages on each platform.

On a pull request, the `pr` job runs `tools/workflow/pr-check.mjs`, a script with no dependencies, on the title and description, which reach it through the environment and never through the script text, where they could inject commands. The title must follow [pull requests](../workflow.md#pull-requests): a Conventional Commits header, `type(scope)!: subject`, with one of the types `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `ci`, `revert` and `build`, an optional lowercase kebab-case scope, a subject that does not start with a capital letter or end with a period, and at most 50 characters in all. The description must link an issue: `Closes`, `Fixes`, `Resolves` or `Refs`, in any case, then `#N` or the issue's URL. A link inside an HTML comment or code does not count, because GitHub links nothing there and the pull request template's example sits in a comment. The script prints one line for each problem, as an error annotation in Actions. Run it the same way before opening a pull request: `PR_TITLE='…' PR_BODY='…' node tools/workflow/pr-check.mjs`. `tools/workflow/commit-title.mjs` holds the header parser, for other tools that read commit subjects.

The last job, `CI`, needs both and passes only when all three platforms passed and the `pr` job passed, or was skipped on a push to `main`. It is the one check the ruleset on `main` requires, so renaming a platform job never breaks protection. It runs even in a cancelled run and fails there, because GitHub counts a skipped check as passing.

A pull request runs CI when it is opened, reopened, pushed to, marked ready for review or edited, and a newer run cancels the older one. An edit to the title, description or base branch runs every job, the platforms included: the newest run on a commit gives its `CI` result, so a run that checked only the text could hide a failure on that commit, and a new base changes the code that is tested. Runs on `main` are never cancelled, so each commit there keeps its own result.

Real agents never run in CI: they need accounts and cost money.

## Screenshots

Nobody runs every platform by hand, so `.github/workflows/screenshots.yml` captures the main screens of a production build on `macos-latest`, `windows-latest` and `ubuntu-24.04` (under `xvfb-run`), on demand, and on pushes to `main` and pull requests that touch `src/`, `tools/` or the workflow itself. On a pull request a newer run cancels the older one; on `main` none is cancelled. Each run uploads one artifact per platform, `screenshots-<OS>`; `gh run download <run id>` fetches them for review. It needs no secrets and publishes nothing beyond those artifacts, so it runs the same on a pull request as on `main`.

`tools/screenshots/capture.mjs`, with no dependencies, does the capturing. It starts the app from `out/` with `--overbench-perf`, a fresh data folder and the fake agent, adds a scratch git project on an unpublished branch with one uncommitted file, and drives the real UI over the Chrome DevTools Protocol in the default 1280 x 820 window at a device scale factor of 2. Only the scale is emulated, so the window controls overlay on Windows and Linux lines up as it does for users; the Windows job first enlarges the runner's 1024 x 768 screen so the window fits. The log notes the window size and the width the thread's scrollbar takes. It writes `<platform>-<screen>-<light|dark>.png` for the welcome screen, the New session screen and its project menu, a finished `/basic-turn` (and the same thread mid-scroll, light only, where overlay scrollbars show), the model menu, a `/permission` request, the terminal panel, the session context menu, the project menu and its Import sessions dialog, the New session agent menu once the fake agent's models are known, all nine Settings sections, the fake agent's page in Settings › Agents and the Settings search results for "proxy". Locally, run `pnpm build`, then `node tools/screenshots/capture.mjs --out <folder>`; `--port` changes the debugging port (default 9230).

## Measuring performance

Budgets are measured on a production build with the fake agent, launched with `--overbench-perf` and `--remote-debugging-port`, and driven by `tools/perf/measure.mjs`, a script with no dependencies that talks to the renderer over the Chrome DevTools Protocol. Either build works:

- unpacked: `pnpm build`, then `pnpm exec electron-vite preview --skipBuild -- --overbench-perf --remote-debugging-port=9222`; development builds list the fake agent on their own;
- packaged: `pnpm package`, then start the app with `OVERBENCH_FAKE_AGENT` set to the path of `tools/fake-agent/main.ts` and the same two flags.

Open a project in the app, leave the window alone, and run `node tools/perf/measure.mjs --port 9222` (`--json` prints the raw numbers). `node tools/perf/run.mjs` does all of it on its own: it starts the build in `out/` with the fake agent, a fresh data folder and a scratch project, through `tools/launch.mjs`, which the screenshot tool shares, runs `measure.mjs` and exits with its code. `.github/workflows/perf.yml` runs it on demand on `macos-latest`, `windows-latest` and `ubuntu-24.04` and uploads the results as `perf-<OS>`; its `ref` and `os` inputs measure another commit or fewer runners, as when bisecting a regression on one platform; runners are virtual machines without a GPU, so their numbers show regressions and platform differences, not what the budgets' machines would measure. The script drives the real UI with real input events: it starts fake-agent sessions from the first project's **+**, choosing the fake agent in the agent menu, each with a short `/status` turn so it is ready before anything is measured, sends `/long-stream` and `/tool-storm` through the composer, imports `history-1000` and `history-4000`, whose first open replays and stores them, and closes and reopens them from the session menu and the sidebar, so the reopens read the stored thread.

| Budget                            | How it is measured                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Launch to first interactive frame | The renderer sends `perf:interactive` after the first frame of the app shell; main records `process.uptime()` then and returns it from `perf:metrics`                                                                                                                                                                                                                                                                                                                               |
| Renderer commits while streaming  | The renderer counts thread store updates per animation frame during `long-stream`                                                                                                                                                                                                                                                                                                                                                                                                   |
| Main-thread long tasks            | A `PerformanceObserver` for `long-animation-frame`, during `long-stream` and `tool-storm`                                                                                                                                                                                                                                                                                                                                                                                           |
| Session switch                    | From the click on a session to the task after the first frame painted with its thread, measured five times against the imported session with 1,000 stored entries, after a switch away. Each switch also reports when it settled, the end of the last frame over 50 ms before a second without one, and how many there were, as do the reopens of 1,000 and 4,000 entries, a switch back to the 4,000-entry session and one to the 1,000-entry session after four others evicted it |
| Keystroke to paint                | A letter typed every 150 ms into the composer while `long-stream` runs, timed from the key event to the start of the frame after the one that shows it. The part before the renderer's handler runs, delivery, is reported apart, as are Event Timing durations; they run to the frame's presentation and so include the OS compositor                                                                                                                                              |
| Agent host memory                 | The working set of the process named OverBench Agent Host in `app.getAppMetrics()`, from `perf:metrics`, after `tool-storm`                                                                                                                                                                                                                                                                                                                                                         |

The script prints a table; the results for each platform are recorded in [`docs/perf/m0.md`](../perf/m0.md) with the date, machine, OS and app version. A change that makes a budget fail is not merged.

- With `--overbench-perf`, the renderer exposes its counters as `window.__overbenchPerf` (`frames()`, `switches()`, `reset()`), which the script reads with `Runtime.evaluate`, and main answers the `perf:metrics` IPC call, which rejects without the flag.
- Main logs the first `perf:interactive` of a launch to stdout as `perf:interactive <ms> ms after launch`, and later ones, from reloads, separately; diagnostics keep it as `main.launchToInteractiveMs`.
- When main itself was started with `--overbench-perf`, it passes the flag to each page with `additionalArguments`, and the preload sets `window.overbench.perf`. It also turns off `backgroundThrottling`, so a window behind others or on another Space still renders every frame and runs its timers on time while it is measured.
