## 3. Ultracode

- **What it is**: since Claude Code 2.1.284, a per-session switch apart from the effort level. While on, the CLI asks for a dynamic workflow (`Workflow` tool) on every substantial task and lifts the subagent concurrency cap. It changes neither the model nor the thinking budget; only `--effort ultracode` and `effortLevel: "ultracode"` also set the effort to `xhigh`. It takes effect only when dynamic workflows are enabled for the account and the model supports `xhigh`.
- **Where its state lives**: in the session's memory. The CLI toggles it with `/effort ultracode`, Tab in the `/effort` slider or `--effort ultracode`; the `ultracode` settings key is read at start and never written. The keyword in a prompt is different: it forces a workflow for that one turn only.
- **What the adapter offers** (`@agentclientprotocol/claude-agent-acp` 0.94.0 and 0.94.1-preview.2): no config option. It does pass `_meta.claudeCode.options.settings` from `session/new` to the SDK, so `{ "ultracode": true }` turns it on for a new session, and since 0.85.0 it keeps `ultracode: true` across effort and model changes. Changing it mid-session means `session/resume` with new settings, which restarts the Claude process and aborts a running turn.
- **Upstream**: issue #725 is open; PR #924 (a boolean option, like Fast mode) and PR #1176 (UltraCode in the effort picker, which conflicts with the 2.1.284 meaning) wait for review.
- **Recommendation**: a switch through `_meta` now, shown with Fast mode in the model menu only when the effort offers `xhigh`, disabled during a turn, with the model button reading "… High · Ultracode" in the max-tier gradient; support PR #924 upstream and move to the adapter's option once it lands.
- **To decide**: whether new sessions start with it off, which overrides a user's own `"ultracode": true` in their Claude settings; and whether a switch between turns may restart the Claude process.
- **Not verified**: that the `_meta` route works in a live session, how long the restart takes, and how `Workflow` tool calls render in the thread.

## 7 and 17. Usage, plan limits and agent facts

- **Context breakdown** (what fills Claude Code's window): the Agent SDK has it (`getContextUsage()`, the `get_context_usage` control request, with used, free, buffer and deferred parts, MCP tools, memory files and skills), but the adapter forwards neither it nor the structured `/context` result; `/context` reaches the client only as markdown in `agent_message_chunk`. The clean route is an extension method upstream, such as `_claude/context_usage` (issue #643 is open; PR #1283 was closed unmerged). Until then the popover can only show used and size. Hidden `/context` turns are not recommended.
- **Claude plan limits**: `usage_update._meta["_claude/rateLimit"]` carries one window per event, only when it changes, and the adapter drops events that arrive in a turn before its first usage update (issue #1127; fix PR #1191 closed unmerged). Available now without new dependencies: ask for raw SDK messages in `session/new` (`_meta.claudeCode.emitRawSDKMessages` with `rate_limit_event` and `system/init`) and read the `_claude/sdkMessage` notifications, which fixes the dropped events. All windows with live percentages exist only in Claude Code's own usage request, which the adapter renders as `/usage` markdown; that also needs an extension method upstream.
- **What other tools do**: Orca, CodexBar and claude-monitor call the undocumented `GET api.anthropic.com/api/oauth/usage` with the OAuth token read from the keychain or `~/.claude/.credentials.json`. Anthropic's terms say developers may not collect or intermediate Claude.ai credentials or session tokens, so this is not recommended.
- **Codex**: its app server has `account/rateLimits/read` and `account/rateLimits/updated`; `codex-acp` 2.2.2 receives them but uses them only for `/status`. Three upstream PRs would forward them (#334, #426, #524; #524 is the one to support). Until then the only acceptable stopgap is a short-lived `codex app-server` started by the agent host on demand. Chosen instead on 2026-10-21: reading `/status` in a hidden session, as for Claude Code's `/usage`, which stays within ACP.
- **OpenCode**: no plan usage over ACP; its only own plan, OpenCode Go, needs the user's Go API key. Show none in M0.
- **Versions and accounts**: `agentInfo.version` is the adapter's (Claude Code's adapter 0.94.0 pins SDK 0.3.303 with Claude Code 2.1.303); Claude Code's own version comes with the raw `system/init` message (`claude_code_version`). Codex's CLI version is not forwarded (an upstream request). Codex's account already arrives in `_auth/status_update`. OpenCode's version is in `agentInfo`; its account can come from `opencode auth list --format json`, run asynchronously.
- **To decide**: whether to adopt the raw-message route now, which upstream requests to file, and what the popover and Settings › Agents show for agents without a source.

## 11. Steering and queued messages

| Agent                            | Steering into a running turn                                                                                                                                           | A second `session/prompt` during a turn                             |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Claude Code (adapter 0.94.0)     | `_session/steering`, advertised in `initialize` `_meta.steering.supported`; preempts the turn and backgrounds a running tool; honours `idleBehavior: "promptRequired"` | Queued by the adapter; the first prompt then ends with `end_turn`   |
| Codex (`codex-acp` 2.2.2)        | The same request, through Codex's `turn/steer`, read at the model's next step; ignores `idleBehavior` (PR #593 open)                                                   | Undefined in 2.2.2; first in, first out on `main` and 2.2.3-preview |
| OpenCode (`opencode acp` 2.0.32) | None                                                                                                                                                                   | Rejected: "Session already has an active ACP prompt"                |

- **ACP**: v1 has nothing; the v2 prompt RFD leaves queueing and steering out; two RFD proposals are open without a champion (#2255, steering; #1261, `session/inject`). `_session/steering` is an unofficial convention of the two adapters.
- **Recommendation**: OverBench owns the queue for every agent, in the agent host: a tray above the composer whose items can be edited, removed, reordered and steered one by one; the head item goes when a turn ends normally; the queue pauses after Stop or an error and is persisted and restored paused. OverBench never sends a concurrent `session/prompt`. Steering only where the agent advertises it, always with `idleBehavior: "promptRequired"`, gated for Codex on a version that honours it. A steered message shows in the thread with a "Steered" label and a pending state. OpenCode gets the queue, with an optional "Send now" that stops the turn and sends.
- **To decide**: what `Enter` does during a turn. Codex CLI, OpenCode and Replit steer by default; Zed and Orca queue. The proposal is `Enter` queues, `Mod+Enter` steers, with a setting to swap them.
- **Not verified**: Claude Code folding a queued prompt mid-turn, Codex 2.2.2 with an overlapping prompt, and whether a steered message is echoed back live.

## 12. Switching sessions

Measured on a production build with the fake agent over CDP:

| Cause                                                                                                                                  | Measured                                                                                                | Fix                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| A session that is not live waits for the agent to start and the whole `session/load` replay before anything but `ThreadSkeleton` shows | The stall in the report                                                                                 | Show the starting state on this path too                                                                                                     |
| The host's replay copies `byId` once per patch (quadratic)                                                                             | `session/load` 94 ms at 1,000 entries, 1.4 s at 4,000, 6.0 s at 8,000                                   | `7dddd70` (4,000 entries: 1,467 ms to 126 ms to first paint in the probe)                                                                    |
| Agents start through `npx -y` on every launch                                                                                          | Claude Code's adapter answers `initialize` in 1.3 to 1.6 s, against 0.18 s running its cached bin       | Resolve the installed bin once (a managed install); not tried in the app                                                                     |
| Restoring the last session at launch waits for `gh auth status`                                                                        | The open starts 0.8 to 1.4 s later than it needs to                                                     | `3e26044`                                                                                                                                    |
| Every switch remounts the whole thread, and mounting history is quadratic: `Clamp` forces a layout per commit, 60 items per prepend    | A cached 4,000-entry session paints in 26 ms, then the renderer is busy 3.5 s with 19 frames over 50 ms | `1365800`: one shared `ResizeObserver` for every `Clamp`, committing before paint so nothing flashes unclamped, plus doubling prepend chunks |
| Leaving and coming back remounts even a warm session                                                                                   | 3.4 s to settle at 4,000 entries                                                                        | Keep the recent sessions mounted with React's `<Activity>` (0.12 s), only after the `Clamp` fix; still one 108 to 250 ms frame on showing    |

Not the cause: the main process (13 ms at most), snapshot transfer (133 KB in 4 to 5 ms), the store update, Shiki and diffs. Streamdown parsing again on every mount is about half the JavaScript of a markdown-heavy switch.

- **The perf script should gain**: a `session/load` reopen at 4,000 entries, a settled time and long frames for cached switches, a switch to an evicted session, and launch to restored thread. The M0 budget measures only first paint, which passes in every case above.
- **To decide**: which of the remaining fixes come into M0, and whether threads beyond a few thousand entries need windowing, which [Architecture](../architecture.md) allows only when measurements show it is needed; these do, past about 8,000 entries.
- **Not measured**: Claude Code's own `session/load` against real transcripts; a diagnostics export from a slow switch would split it.
